# ⚙️ Generated Values

## 🔎 Core Concept

Database columns can have their values generated automatically.

Common examples:

- Primary keys generated by the database.
- Default values.
- Computed columns.
- Values generated when a row is inserted or updated.

```text
Application
     │
     ▼
Entity Property
     │
     ▼
Value Generation Configuration
     │
     ▼
EF Core / Database
     │
     ▼
Generated Value
```

---

# 🟦 1. Default Values

A relational column can have a default value.

If an INSERT does not provide a value:

```text
INSERT without value
        ↓
Database Default
        ↓
Value Stored
```

### Fluent API

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Rating)
    .HasDefaultValue(3);
```

A SQL expression can also generate the default:

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Created)
    .HasDefaultValueSql("getdate()");
```

### 🧠 Adding a New Column

If a new property with a default value is added through a migration:

```text
Existing Rows
     ↓
New Column Added
     ↓
Default Value Applied

Future Inserts
     ↓
No value supplied
     ↓
Default Value Applied
```

---

# 🏷️ Named Default Constraints

For SQL Server, starting with **EF Core 10**, default constraints can be explicitly named.

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Rating)
    .HasDefaultValue(3, "DF_Blog_Rating");
```

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Created)
    .HasDefaultValueSql(
        "getdate()",
        "DF_Blog_Created");
```

### Automatic Naming

```csharp
protected override void OnModelCreating(
    ModelBuilder modelBuilder)
{
    modelBuilder.UseNamedDefaultConstraints();
}
```

> ⚠️ When existing migrations are present, the next migration can rename all default constraints in the model.

# 🧮 2. Computed Columns

A computed column gets its value from a database expression.

```csharp
modelBuilder.Entity<Person>()
    .Property(p => p.DisplayName)
    .HasComputedColumnSql(
        "[LastName] + ', ' + [FirstName]");
```

### Virtual Computed Column

```text
Row Read
   ↓
Database evaluates expression
   ↓
Computed Value returned
```

The value is computed when it is read.

### Stored / Persisted Computed Column

```csharp
modelBuilder.Entity<Person>()
    .Property(p => p.NameLength)
    .HasComputedColumnSql(
        "LEN([LastName]) + LEN([FirstName])",
        stored: true);
```

```text
INSERT / UPDATE
      ↓
Compute Value
      ↓
Store Value on Disk
```

> ⭐ `stored: true` creates a stored/persisted computed column where supported.

---

# 🔑 3. Primary Key Value Generation

By convention, non-composite primary keys of type:

```text
short
int
long
Guid
```

are configured for value generation when values are not supplied.

Example:

```text
SQL Server
   ↓
int Primary Key
   ↓
IDENTITY
```

For GUID keys, the provider can generate GUID values automatically.

---

# 🛠️ 4. Explicit Value Generation

Value generation can also be configured for **non-key properties**.

## Generate on Add

### Data Annotation

```csharp
[DatabaseGenerated(
    DatabaseGeneratedOption.Identity)]
public DateTime Inserted { get; set; }
```

### Fluent API

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Inserted)
    .ValueGeneratedOnAdd();
```

```text
INSERT
  ↓
Property Value Generated
```

---

## Generate on Add or Update

### Data Annotation

```csharp
[DatabaseGenerated(
    DatabaseGeneratedOption.Computed)]
public DateTime LastUpdated { get; set; }
```

### Fluent API

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.LastUpdated)
    .ValueGeneratedOnAddOrUpdate();
```

```text
INSERT ──┐
         ├──→ Generate Value
UPDATE ──┘
```

---

# ⚠️ Value Generation Does Not Define HOW the Value Is Generated

`ValueGeneratedOnAdd()` or `ValueGeneratedOnAddOrUpdate()` tells EF Core **when** a value is expected to be generated.

It does not necessarily define **how** it is generated.

```text
EF Core
   ↓
When should value be generated?
   ↓
Provider / Database
   ↓
How is value generated?
```

Provider behavior varies.

Examples from SQL Server:

- GUID primary keys can use provider-side generation.
- `byte[]` properties configured as generated and concurrency tokens can map to `rowversion`.
- Simply calling `ValueGeneratedOnAdd()` on a `DateTime` does not by itself create a database-generated timestamp.

> ⭐ Always check the database provider's value-generation capabilities.

# 🕒 5. Date/Time Value Generation

EF Core providers generally do not automatically configure date/time generation because databases support different strategies.

## Creation Timestamp

For "created at" values, a database default is commonly used.

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.Created)
    .HasDefaultValueSql("GETDATE()");
```

Choose the appropriate database function, for example:

```text
GETDATE()
GETUTCDATE()
```

depending on the application's requirements.

---

## Update Timestamp

A computed column is often not suitable for expressions such as `GETDATE()` for last-update timestamps.

A database trigger can be used instead:

```text
UPDATE Blog
     ↓
Database Trigger
     ↓
LastUpdated = GETDATE()
```

> 💡 Trigger creation can be managed through raw SQL in migrations.

---

# ✏️ 6. Overriding Value Generation

A value-generated property can sometimes still receive an explicit value.

```text
Value Generation Configured
          ↓
Can explicit value be supplied?
          │
     ┌────┴────┐
    YES        NO
     │          │
Override      Database /
Generation    Provider
               Generates
```

To provide an explicit value, use a value different from the CLR default where the configured generation strategy allows it.

Examples:

```text
string → null
int    → 0
Guid   → Guid.Empty
```

So an explicit value is typically a **non-default CLR value**.

### ⚠️ Important

Computed columns cannot generally be overridden by simply assigning an explicit value.

For SQL Server, explicitly inserting into an `IDENTITY` column also fails by default unless the appropriate SQL Server mechanism is used.

---

# 🛠️ Allow Explicit Values for Add/Update Generated Properties

For a property configured as generated on add/update:

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.LastUpdated)
    .ValueGeneratedOnAddOrUpdate()
    .Metadata
    .SetAfterSaveBehavior(
        PropertySaveBehavior.Save);
```

```text
Value Generated Property
        +
Explicit Save Behavior
        ↓
Application can provide a value
```

---

# 🚫 7. No Value Generation

Most properties normally have **no value generation configured**.

That means:

```text
Application
    ↓
Provides Value
    ↓
Entity Added
    ↓
Database
```

The application must assign the value before adding a new entity to the context.

---

# ⛔ Disabling Convention-Based Generation

For example, an `int` primary key is commonly configured for value generation on SQL Server.

Disable it with:

### Data Annotation

```csharp
[DatabaseGenerated(
    DatabaseGeneratedOption.None)]
public int BlogId { get; set; }
```

### Fluent API

```csharp
modelBuilder.Entity<Blog>()
    .Property(b => b.BlogId)
    .ValueGeneratedNever();
```

```text
Default Convention
     ↓
Generated Key

ValueGeneratedNever()
     ↓
Application must supply Key
```

---

# 🆚 Default vs Computed vs Explicit Generation

| Configuration | When Value Is Generated | Typical Example |
|---|---|---|
| `HasDefaultValue()` | Insert when value not supplied | `Rating = 3` |
| `HasDefaultValueSql()` | Insert using SQL expression | `GETDATE()` |
| `HasComputedColumnSql()` | Database computes from expression | `DisplayName` |
| `ValueGeneratedOnAdd()` | On insert | `Inserted` |
| `ValueGeneratedOnAddOrUpdate()` | On insert/update | `LastUpdated` |
| `ValueGeneratedNever()` | Never | Application supplies value |

---

# ⭐ Key Rules to Remember

```text
1. Generated values can come from EF Core, the provider,
   or the database depending on the configuration.

2. Default values are used when an INSERT does not provide a value.

3. HasDefaultValue() uses a fixed default value.

4. HasDefaultValueSql() uses a SQL expression.

5. Computed columns calculate values from database expressions.

6. Computed columns may be virtual or stored/persisted.

7. Primary keys such as int/long/short/Guid are commonly
   configured for generation by convention when non-composite.

8. ValueGeneratedOnAdd() means generated on INSERT.

9. ValueGeneratedOnAddOrUpdate() means generated on INSERT and UPDATE.

10. These APIs describe WHEN generation happens;
    the provider determines HOW generation works.

11. DateTime generation is generally not configured automatically
    because provider/database strategies differ.

12. Last-updated timestamps may require a database trigger.

13. Explicit values can sometimes override value generation,
    depending on the configured generation mechanism.

14. Computed columns cannot generally be overridden like
    normal default-generated properties.

15. ValueGeneratedNever() disables convention-based generation.

16. Provider-specific behavior must always be considered.
```

# ⚡ 30-Second Mental Model

```text
                     GENERATED VALUES
                            │
           ┌────────────────┼────────────────┐
           │                │                │
           ▼                ▼                ▼
        DEFAULT          COMPUTED        EXPLICIT
           │                │                │
     Missing on INSERT   DB Expression   Application Value
           │                │                │
           ▼                ▼                ▼
   HasDefaultValue()   HasComputed...   Normal Property
   HasDefaultValueSql()


WHEN?
│
├── ValueGeneratedOnAdd()
│       ↓
│     INSERT
│
├── ValueGeneratedOnAddOrUpdate()
│       ↓
│     INSERT + UPDATE
│
└── ValueGeneratedNever()
        ↓
      Application supplies value
```

> 🎯 **Core takeaway:** EF Core value generation controls **when values are expected to be generated**, while the provider/database determines **how** they are generated. The main patterns are **defaults, computed columns, generated-on-add, generated-on-add-or-update, and no generation**.
