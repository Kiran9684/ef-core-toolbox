# 🔌 Disconnected Entities in EF Core

## 🔎 Overview

Normally, a `DbContext` tracks the entities it queries.

```text
Query Database
      ↓
Entity Loaded
      ↓
DbContext Tracks Entity
      ↓
Modify Entity
      ↓
SaveChanges()
      ↓
Database Updated
```

In a disconnected scenario, the entity is no longer associated with the original `DbContext`.

```text
Request 1
─────────

Query
  ↓
DbContext Tracks Entity
  ↓
Send Entity to Client
  ↓
DbContext Ends


Client / External Layer
───────────────────────

Modify Entity
  ↓
Send Entity Back


Request 2
─────────

New DbContext
  ↓
❓ Is Entity New?
❓ Is Entity Existing?
❓ Was Something Deleted?
  ↓
Set Correct EntityState
  ↓
SaveChanges()
```

> 👉 The new `DbContext` must determine the correct `EntityState`.

---

## 🌐 Common Disconnected Scenarios

* 🌐 **Web applications**
* 🔌 **Web APIs**
* ⏱️ **Background jobs**
* 📡 **Distributed services**

### Example

```text
API Request 1
     ↓
GET /blogs/1
     ↓
Entity sent to client
     ↓
Client modifies data
     ↓
API Request 2
     ↓
PUT /blogs/1
     ↓
New DbContext handles update
```

---

## 🧠 Key Best Practice

### Use a Short-Lived DbContext Per Unit of Work

```text
Create DbContext
      ↓
Attach / Query Entities
      ↓
Perform Work
      ↓
SaveChanges()
      ↓
Dispose DbContext
```

### Benefits

* Prevents long-running tracking.
* Avoids stale entities.
* Reduces memory usage.
* Avoids multiple tracked instances with the same primary key.
* Fits naturally with web request lifetimes.

> 👉 **One DbContext = One Unit of Work**

# 🆔 Identifying New vs Existing Entities

The biggest question in disconnected scenarios is:

```text
Incoming Entity
      ↓
Does it represent a NEW row?
      OR
Does it represent an EXISTING row?
```

---

## 1️⃣ Client Explicitly Identifies the Operation

The simplest approach is to already know the operation.

```text
POST   → Create
PUT    → Update
DELETE → Delete
```

### Insert

```csharp
context.Add(entity);

await context.SaveChangesAsync();
```

### Update

```csharp
context.Update(entity);

await context.SaveChangesAsync();
```

---

# 🔑 Auto-Generated Keys

For keys generated by the database, EF Core can often determine whether an entity is new.

```text
Primary Key = Default Value
        ↓
      NEW
        ↓
     INSERT


Primary Key = Set
        ↓
    EXISTING
        ↓
     UPDATE
```

### Example

```csharp
public static bool IsItNew(Blog blog)
    => blog.BlogId == 0;
```

### EF Core Built-In Check

```csharp
public static bool IsItNew(DbContext context, object entity)
    => !context.Entry(entity).IsKeySet;
```

---

# ⚙️ Using `Update()` with Auto-Generated Keys

For entities with generated keys:

```csharp
public static async Task InsertOrUpdate(
    DbContext context,
    object entity)
{
    context.Update(entity);

    await context.SaveChangesAsync();
}
```

### Mental Model

```text
context.Update(entity)
        ↓
Is Key Set?
   ↙         ↘
 NO          YES
 ↓            ↓
Added      Modified
 ↓            ↓
INSERT      UPDATE
```

> 👉 `Update()` can therefore handle both insert and update for generated-key entities.

---

# 🔐 Non-Generated Keys

If the key is assigned manually, EF Core cannot reliably determine whether the row already exists.

You usually need to query the database.

```csharp
public static async Task InsertOrUpdate(
    BloggingContext context,
    Blog blog)
{
    var existingBlog =
        await context.Blogs.FindAsync(blog.BlogId);

    if (existingBlog == null)
    {
        context.Add(blog);
    }
    else
    {
        context.Entry(existingBlog)
            .CurrentValues
            .SetValues(blog);
    }

    await context.SaveChangesAsync();
}
```

### Flow

```text
Incoming Entity
      ↓
Find Existing Entity
      ↓
Exists?
 ↙         ↘
NO          YES
↓            ↓
Add()      SetValues()
↓            ↓
INSERT      UPDATE
```

---

# 💡 `SetValues()`

```csharp
context.Entry(existingBlog)
    .CurrentValues
    .SetValues(blog);
```

## What It Does

Copies scalar property values from the disconnected entity to the tracked entity.

```text
Incoming Blog
     ↓
SetValues()
     ↓
Tracked Blog
     ↓
Change Detection
     ↓
Only Changed Properties
     ↓
UPDATE
```

### Important Rules

* Updates scalar properties.
* Does **not** automatically update navigation collections.
* Only marks properties as modified when values differ.
* If nothing changed, no unnecessary update is sent.

> ⭐ `SetValues()` does **NOT** copy the entire object graph.

# 🌳 What Is an Entity Graph?

A graph is a connected group of related entities.

### Example

```text
Blog
 │
 ├── Post 1
 │
 ├── Post 2
 │
 └── Post 3
```

```csharp
var blog = new Blog
{
    Url = "http://sample.com",

    Posts = new List<Post>
    {
        new Post { Title = "Post 1" },
        new Post { Title = "Post 2" }
    }
};
```

The graph contains:

```text
Blog (Root)
   ↓
Posts (Children)
```

---

# 🧭 EF Core Graph Traversal

Methods such as:

* `Add()`
* `Attach()`
* `Update()`

can traverse the graph.

```text
Root Entity
     ↓
EF Core Traverses Navigations
     ↓
Child Entities
     ↓
Assign Entity States
```

---

```csharp
context.Add(blog);

await context.SaveChangesAsync();
```

### Result

```text
Blog  → Added
Post1 → Added
Post2 → Added
```

```text
SaveChanges()
      ↓
INSERT Blog
INSERT Posts
```

---

# 🔄 Update an Entire Graph

```csharp
context.Update(blog);

await context.SaveChangesAsync();
```

### Result

```text
Blog  → Modified
Post1 → Modified
Post2 → Modified
```

> ⚠️ **Be careful:** `Update()` can mark the entire graph as modified.

# 🔀 Mixed Graph: New + Existing Entities

### Example

```text
Blog (Existing)
 │
 ├── Post 1 (Existing)
 ├── Post 2 (Existing)
 └── Post 3 (New)
```

With auto-generated keys:

```csharp
context.Update(blog);

```

### EF Core Decision

```text
Entity Key Set?
     ↓
 ┌───────────────┐
 │               │
 NO             YES
 │               │
Added         Modified
 │               │
INSERT         UPDATE
```

# 🔎 Identity Resolution

EF Core can track only one instance of an entity with the same primary key.

### Problem

```csharp
var blogFromDb = await context.Blogs
    .Include(b => b.Posts)
    .FirstAsync(b => b.BlogId == 1);

var duplicateBlog = new Blog
{
    BlogId = 1
};

context.Attach(duplicateBlog); // ❌ Conflict
```

### Why?

```text
DbContext

Blog Id = 1
      │
      ├── Instance A
      │
      └── Instance B ❌
```

EF Core does not know which instance represents the correct state.

### Best Practice

* Keep contexts short-lived.
* Avoid duplicate entity instances.
* Ensure each primary key maps to one tracked object.
* Consolidate duplicates early.

---

# 🔀 Handling Mixed Graphs Manually

For non-generated keys, load the existing graph first.

```csharp
var existingBlog = await context.Blogs
    .Include(b => b.Posts)
    .FirstOrDefaultAsync(
        b => b.BlogId == blog.BlogId);
```

Then:

```text
Existing Blog?
     ↓
 ┌───────────────┐
 │               │
 NO             YES
 │               │
Add Graph      Compare Graph
 │               │
INSERT       Insert / Update
```

---

# 🔄 Insert or Update a Graph

```csharp
public static async Task InsertOrUpdateGraph(
    BloggingContext context,
    Blog blog)
{
    var existingBlog = await context.Blogs
        .Include(b => b.Posts)
        .FirstOrDefaultAsync(
            b => b.BlogId == blog.BlogId);

    if (existingBlog == null)
    {
        context.Add(blog);
    }
    else
    {
        context.Entry(existingBlog)
            .CurrentValues
            .SetValues(blog);

        foreach (var post in blog.Posts)
        {
            var existingPost =
                existingBlog.Posts
                    .FirstOrDefault(
                        p => p.PostId == post.PostId);

            if (existingPost == null)
            {
                existingBlog.Posts.Add(post);
            }
            else
            {
                context.Entry(existingPost)
                    .CurrentValues
                    .SetValues(post);
            }
        }
    }

    await context.SaveChangesAsync();
}
```

### Graph Processing Model

```text
BLOG
 │
 ├── Root
 │     ↓
 │   SetValues()
 │
 └── POSTS
       ↓
   For Each Incoming Post
       ↓
   Exists?
    ↙     ↘
   NO      YES
   ↓        ↓
 INSERT   UPDATE
```

# 🗑️ Handling Deletes in Disconnected Graphs

Deletes are more difficult because an entity may simply be missing from the incoming graph.

### Example

#### Database

```text
Blog
 ├── Post 1
 ├── Post 2
 └── Post 3
```

#### Incoming Graph

```text
Blog
 ├── Post 1
 └── Post 3
```

### Question

```text
Where is Post 2?
        ↓
Should it be deleted?
```

---

# 🟦 Two Delete Strategies

## 1️⃣ Soft Delete

Instead of removing the row:

```text
IsDeleted = false
        ↓
IsDeleted = true
```

### Example

```csharp
post.IsDeleted = true;
```

Usually combined with query filters.

### Benefit

```text
DELETE
   ↓
Becomes
   ↓
UPDATE
```

The data remains in the database.

---

## 2️⃣ True Delete

Actually remove the row.

```csharp
context.Remove(post);
```

This requires a graph diff.

```text
Existing Graph
       VS
Incoming Graph
       ↓
Compare Entities
       ↓
Missing Entity?
       ↓
DELETE
```

---

# 🔄 Insert + Update + Delete Graph

```csharp
public static async Task InsertUpdateOrDeleteGraph(
    BloggingContext context,
    Blog blog)
{
    var existingBlog = await context.Blogs
        .Include(b => b.Posts)
        .FirstOrDefaultAsync(
            b => b.BlogId == blog.BlogId);

    if (existingBlog == null)
    {
        context.Add(blog);
    }
    else
    {
        // Update Blog
        context.Entry(existingBlog)
            .CurrentValues
            .SetValues(blog);

        // Insert / Update Posts
        foreach (var post in blog.Posts)
        {
            var existingPost =
                existingBlog.Posts
                    .FirstOrDefault(
                        p => p.PostId == post.PostId);

            if (existingPost == null)
            {
                existingBlog.Posts.Add(post);
            }
            else
            {
                context.Entry(existingPost)
                    .CurrentValues
                    .SetValues(post);
            }
        }

        // Delete Missing Posts
        foreach (var post in existingBlog.Posts)
        {
            if (!blog.Posts.Any(
                p => p.PostId == post.PostId))
            {
                context.Remove(post);
            }
        }
    }

    await context.SaveChangesAsync();
}
```

```text
Incoming Graph
      ↓
Load Existing Graph
      ↓
Compare Root
      ↓
Update Root Values
      ↓
Compare Children
      │
      ├── New Child?
      │      ↓
      │    INSERT
      │
      ├── Existing Child?
      │      ↓
      │    UPDATE
      │
      └── Missing Child?
             ↓
           DELETE
```

# ⚠️ Important: `SetValues()` and Navigation Properties

```csharp
context.Entry(existingBlog)
    .CurrentValues
    .SetValues(blog);
```

This updates only:

### Blog Scalar Properties

* ✔ `Name`
* ✔ `Url`
* ✔ `Rating`
* ✔ Other scalar fields

It does **NOT** automatically handle:

* ❌ `Posts` collection
* ❌ New `Posts`
* ❌ Removed `Posts`
* ❌ Updated `Posts`

Therefore, related entities must be handled separately.

```text
Root Entity
    ↓
SetValues()
    ↓
Children
    ↓
Loop + Compare
    ↓
Insert / Update / Delete
```

# 🕸️ TrackGraph API

EF Core internally traverses entity graphs when using:

* `Add()`
* `Attach()`
* `Update()`

`TrackGraph()` exposes this behavior and lets you decide the state of every entity.

---

# 🎯 Entity States

```text
EntityState.Added
        ↓
      INSERT


EntityState.Modified
        ↓
      UPDATE


EntityState.Deleted
        ↓
      DELETE


EntityState.Unchanged
        ↓
   NO DATABASE ACTION
```

---

# 🟦 TrackGraph Example

```csharp
public static async Task SaveAnnotatedGraph(
    DbContext context,
    object rootEntity)
{
    context.ChangeTracker.TrackGraph(
        rootEntity,
        n =>
        {
            var entity =
                (EntityBase)n.Entry.Entity;

            n.Entry.State =
                entity.IsNew
                    ? EntityState.Added
                    : entity.IsChanged
                        ? EntityState.Modified
                        : entity.IsDeleted
                            ? EntityState.Deleted
                            : EntityState.Unchanged;
        });

    await context.SaveChangesAsync();
}
```

### Flow

```text
Root Entity
      ↓
TrackGraph()
      ↓
Traverse Entire Graph
      ↓
For Each Entity
      ↓
Check Client Flags
      ↓
┌──────────────────────────────┐
│ IsNew?     → Added           │
│ IsChanged? → Modified        │
│ IsDeleted? → Deleted         │
│ Otherwise  → Unchanged       │
└──────────────────────────────┘
      ↓
SaveChanges()
```

---

# 💡 Why Use `TrackGraph()`?

Useful when the client sends metadata describing each entity.

### Example

```text
Blog
 │
 ├── Post 1 → Existing
 ├── Post 2 → Changed
 ├── Post 3 → New
 └── Post 4 → Deleted
```

The client can annotate entities, and `TrackGraph()` converts those decisions into EF Core states.

---

# ⭐ Key Rules & Distinctions

| Concept                | Important Point                                                   |
| ---------------------- | ----------------------------------------------------------------- |
| Connected              | Same `DbContext` tracks entities                                  |
| Disconnected           | Different contexts handle query and save                          |
| Best Practice          | Short-lived `DbContext` per unit of work                          |
| Generated Keys         | `IsKeySet` helps determine new vs existing                        |
| `Add()`                | Marks entities for insertion                                      |
| `Update()`             | Marks entities as modified; can detect new generated-key entities |
| `SetValues()`          | Copies scalar values only                                         |
| Navigation Collections | Must be handled separately                                        |
| Identity Resolution    | Only one tracked instance per primary key                         |
| Graph                  | Connected entities through navigation properties                  |
| Missing Child          | May require explicit delete                                       |
| Soft Delete            | Update a flag instead of removing the row                         |
| `TrackGraph()`         | Custom state assignment while traversing a graph                  |

# ⭐ Golden Mental Model

## Connected

```text
Query → Track → Modify → Save
```

## Disconnected

```text
Query → Context Ends → Client Modifies
                    ↓
              New Context
                    ↓
            Determine State
                    ↓
                 Save
```

> ⭐ **Disconnected EF Core is mainly about correctly determining entity state and synchronizing the incoming object graph with the database.**
