# 🗃️ Managing Migrations

As the EF Core model changes during development, migrations are **added, reviewed, shared through source control, and sometimes removed**.

```text
Model Change
     ↓
Add Migration
     ↓
Review Migration
     ↓
Commit to Source Control
     ↓
Apply to Database
```

> ⭐ Before managing migrations, install the **EF Core command-line tools**.

---

# 🏗️ Different Project / Startup Project

In an N-tier solution, the `DbContext` and migrations may live in a different project from the application that starts the application.

```text
MyPortfolio.Web
      │
      └── Startup Project

MyPortfolio.DataAccess
      │
      ├── DbContext
      └── Migrations
```

Specify both explicitly when required:

```bash
dotnet ef migrations add MigrationName \
    --project MyPortfolio.DataAccess \
    --startup-project MyPortfolio.Web
```

> 💡 `--project` identifies the target project containing the EF Core artifacts, while `--startup-project` identifies the project used to run/configure the application.

After changing the model:

### .NET CLI

```bash

```

### Visual Studio

```powershell
Add-Migration AddBlogCreatedTimestamp
```

```text
Model Change
     ↓
migrations add
     ↓

```

### 🏷️ Migration Naming

A migration name works much like a **commit message**.

Good:

```text
AddBlogCreatedTimestamp
RenameCustomerNameToFullName
AddOrderAuditTable
```

> ⭐ Use descriptive names so the migration history clearly communicates what changed.

# 📁 Files Created by a Migration

A migration normally adds three important files under the `Migrations` directory:

```text
Migrations/
│
├── XXXXXXXXXXXXXX_AddBlogCreatedTimestamp.cs
│      └── Up()   → Apply changes
│      └── Down() → Revert changes
│
├── XXXXXXXXXXXXXX_AddBlogCreatedTimestamp.Designer.cs
│      └── Migration metadata
│
└── MyContextModelSnapshot.cs
       └── Current model snapshot
```

### 🧠 What Each File Does

| File | Purpose |
|---|---|
| Migration `.cs` | Contains `Up()` and `Down()` operations |
| `.Designer.cs` | Contains migration metadata used by EF Core |
| `ModelSnapshot.cs` | Stores the current model state used to calculate future changes |

> ⭐ The timestamp in the migration filename helps keep migrations in **chronological order**.

# 🔍 Always Review Generated Migrations

EF Core generally generates useful migration code, but you should **always inspect it**.

```text
Model Change
     ↓
Migration Generated
     ↓
👀 Review
     ↓
Does it represent the intended change?
     │
   ┌─┴─┐
  YES  NO
   │    │
   │    └── Modify Migration
   ↓
Apply
```

> ⚠️ Never assume generated migration code always understands the developer's intent.

# 🏷️ Column Rename Example

Suppose:

```text
Name
 ↓
FullName
```

EF Core may generate:

```csharp
migrationBuilder.DropColumn(
    name: "Name",
    table: "Customers");

migrationBuilder.AddColumn<string>(
    name: "FullName",
    table: "Customers",
    nullable: true);
```

EF Core cannot always know whether:

```text
DROP + ADD
```

means:

```text
❌ Delete old column
+
✅ Create a completely new column
```

or:

```text
✅ Rename existing column
```

### ⚠️ Risk

Applying the generated migration as-is can lose existing customer names.

### ✅ Correct Migration

```csharp
migrationBuilder.RenameColumn(
    name: "Name",
    table: "Customers",
    newName: "FullName");
```

```text
Name
 ↓
RenameColumn()
 ↓
FullName

✅ Existing data preserved
```

> ⭐ A migration warning about possible data loss should trigger an especially careful review.

# 🔄 Data Transformation with Raw SQL

Sometimes a schema change requires **data migration**, not just schema migration.

Example:

```text
FirstName + LastName
        ↓
     FullName
```

EF Core may generate:

```text
Drop FirstName
Drop LastName
Add FullName
```

That would lose the original data.

### ✅ Better Migration Sequence

```csharp
migrationBuilder.AddColumn<string>(
    name: "FullName",
    table: "Customer",
    nullable: true);

migrationBuilder.Sql("""
    UPDATE Customer
    SET FullName = FirstName + ' ' + LastName;
    """);

migrationBuilder.DropColumn(
    name: "FirstName",
    table: "Customer");

migrationBuilder.DropColumn(
    name: "LastName",
    table: "Customer");
```

```text
1. Add FullName
       ↓
2. Copy existing data
       ↓
3. Drop FirstName / LastName
```

> ⭐ When a schema change also transforms existing data, **preserve the data first, then remove the old structure**.

# 🧩 Arbitrary Database Changes with Raw SQL

Migrations can also manage database objects that EF Core does not directly model.

Examples:

```text
Stored Procedures
Functions
Triggers
Views
Full-Text Search
```

Create an empty migration:

```bash
dotnet ef migrations add AddFullNameProcedure
```

Then add SQL manually:

```csharp
migrationBuilder.Sql("""
    EXEC ('CREATE PROCEDURE getFullName
        @LastName nvarchar(50),
        @FirstName nvarchar(50)
    AS
        RETURN @LastName + @FirstName;');
    """);
```

```text
Empty Migration
      ↓
Add Raw SQL
      ↓
Custom Database Object
```

---

# 🧠 Why `EXEC(...)` Can Be Used

With SQL Server, `EXEC('...')` executes the supplied string as SQL.

It is useful when:

- A statement must be the first or only statement in a SQL batch.
- Parser issues occur in idempotent migration scripts.
- The SQL references columns that may not exist at an earlier point in the migration sequence.

```text
migrationBuilder.Sql()
        ↓
EXEC('...')
        ↓
SQL Server executes string
```

---

# 💾 Migration Transactions & Raw SQL

EF Core normally wraps each migration in its own transaction when the database provider supports it.

However, some operations cannot run inside a transaction.

In such cases:

```csharp
migrationBuilder.Sql(
    sql,
    suppressTransaction: true);
```

```text
Migration
   ↓
Transaction
   │
   ├── Normal operation ✅
   │
   └── Operation requiring no transaction
              ↓
      suppressTransaction: true
```

> ⚠️ Use `suppressTransaction: true` only when the database operation requires it.

# ➖ Removing a Migration

Sometimes a migration was created but **has not been applied**, and you realize the model needs more changes.

### .NET CLI

```bash
dotnet ef migrations remove
```

### Visual Studio

```powershell
Remove-Migration
```

```text
Last Migration
      ↓
Remove
      ↓
Change Model
      ↓
Add Migration Again
```

> ⚠️ **Do not remove migrations that have already been applied to production.** Doing so can break the migration history and prevent safe rollback of those migrations.

# 🔎 Checking for Pending Model Changes

Sometimes the model has changed but a migration has not been created.

Use:

```bash
dotnet ef migrations has-pending-model-changes
```

Or programmatically:

```csharp
context.Database.HasPendingModelChanges();
```

```text
Current Model
      ↓
Compare with Last Migration
      ↓
Changes Found?
   ┌──────┴──────┐
  YES            NO
   ↓              ↓
Pending         In Sync
Migration
```

### 🧪 Useful for Tests

The programmatic API can be used in a test that fails when developers forget to create a migration.

```text
Model Change
     ↓
No Migration
     ↓
Unit Test
     ↓
❌ Fail
```

# ♻️ Resetting All Migrations

In extreme cases, a project may need to completely reset its migration history.

## 🧹 Development Reset

If the database can be recreated:

```text
Delete Migrations Folder
        +
Drop Database
        ↓
Create New Initial Migration
```

The new initial migration represents the current model/schema.

# 🧩 Squashing Migrations Without Losing Data

Migration history can also be consolidated into a single migration.

This is commonly called **squashing**.

### High-Level Flow

```text
Many Old Migrations
        ↓
Back Up Database
        ↓
Clear Migration History
        ↓
Delete Migrations Folder
        ↓
Create New Migration
        ↓
Database Already Has Schema
        ↓
Mark New Migration As Applied
```

### Steps

```text
1. Back up the database.

2. Delete all rows from the migrations history table.

3. Delete the Migrations folder.

4. Create a new migration.

5. Generate a SQL script for the new migration.

6. Record the new migration as already applied,
   because the database tables already exist.
```

For SQL Server, the history table is commonly:

```sql
DELETE FROM [__EFMigrationsHistory];
```

Then the new migration ID and EF Core product version can be recorded:

```sql
INSERT INTO [__EFMigrationsHistory]
    ([MigrationId], [ProductVersion])
VALUES
    (N'<full_migration_timestamp_and_name>',
     N'<EF_version>');
```

> ⚠️ Squashing is a **manual and sensitive operation**. Always back up the database first.

# ⭐ Key Rules to Remember

```text
1. Install EF Core tools before managing migrations.

2. Use --project and --startup-project when
   DbContext/migrations and application startup
   are in different projects.

3. Migration names should clearly describe the change.

4. A migration normally creates:
   → Migration file
   → Designer file
   → Model snapshot

5. Up() applies a migration.
   Down() reverts it.

6. The model snapshot is used when calculating
   changes for the next migration.

7. Migration files should be stored in source control.

8. Always review generated migrations before applying them.

9. EF Core may interpret a rename as DROP + ADD,
   which can cause data loss.

10. Use RenameColumn() when the intention is a rename.

11. When transforming existing data, add the new structure,
    copy the data, then remove the old structure.

12. migrationBuilder.Sql() allows arbitrary SQL in migrations.

13. Raw SQL can manage stored procedures, functions,
    triggers, views, and other database objects.

14. EXEC('...') can help with SQL Server batch/parser
    requirements in migration scripts.

15. EF Core normally wraps migrations in transactions,
    but suppressTransaction can be used where required.

16. Remove migrations only when they have not been
    deployed to production.

17. Use migrations list / Get-Migration to inspect the
    migration chain.

18. has-pending-model-changes() helps detect model changes
    that do not yet have a migration.

19. A migration can be reset completely by deleting
    migrations and recreating the database in suitable
    development scenarios.

20. Migration history can be squashed into a single migration,
    but this requires careful manual database work and backup.
```
